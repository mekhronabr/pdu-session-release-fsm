# Реализация процедуры релиза PDU сессии с помощью конечного автомата

## Введение

Цель этого практического задания - познакомить c одним из способов программирования логики сетевых сервисов, который применяется для реализации процедур, описанных в стандартах 3gpp. 

Вам предлагается реализовать логику одной из процедур в виде конечного автомата, реагирующего на асинхронные сетевые события - входящие запросы к сервису и ответы на исходящие запросы, сделанные самим сервисом. Конечные автоматы хорошо подходят для реализации логики, когда сервис заранее не знает, какое именно событие произойдёт следующим. 

Для знакомства с конечными автоматами можно, например, прочитать статью [Понятие о конечных автоматах: руководство разработчика по предсказуемой логике приложений](https://habr.com/ru/companies/piter/articles/1039106/). В ней описаны плюсы и ограничения данного подхода, а также даны примеры задач, где автоматы подходят хорошо или, наоборот, плохо.

Для знакомства с асинхронным программированием можно прочитать первую половину статьи [Корутины C++ для чайников: пишем асинхронный веб-клиент](https://habr.com/ru/articles/798935/). Вторая половина статьи посвящена сопрограммам (корутинам), которые во многих случаях позволяют писать более простой код, чем конечные автоматы, но в этой практической работе вам предстоит реализовать процедуру, где сервис реагирует на разнообразные сетевые события, и такой сценарий удобнее реализовывать с помощью конечного автомата.

## Процедура релиза PDU сессии

В стандартах 3gpp описаны различные сценарии, где SMF, получив уведомление о некоем событии, инициирует релиз PDU сессии -- освобождение ресурсов опорной сети, базовой станции и мобильного телефона. Подробнее о процедуре релиза сессии можно прочитать в [TS 23.502, 4.3.4.2 UE or network requested PDU Session Release](https://www.etsi.org/deliver/etsi_ts/123500_123599/123502/17.04.00_60/ts_123502v170400p.pdf).

Событием, инициировавшим релиз, может быть запрос от UPF с отчётом, содержим флаг PSDBU (PFCP Session Deleted By the UP function). В этом случае PFCP сессию удалять не нужно, надо освободить только ресурсы базовой станции и мобильного телефона. Подробнее -- в [3GPP TS 29.244, 5.18.2 UP Function Initiated PFCP Session Release](https://www.etsi.org/deliver/etsi_ts/129200_129299/129244/17.05.00_60/ts_129244v170500p.pdf).

## Задача

Вам предлагается написать конечный автомат, реализующий упрощённый вариант логики работы SMF в описанной выше ситуации.

После получения отчёта от UPF, SMF сначала отсылает на него ответ, а затем запускает процедуру релиза сессии -- автомат `ReleaseProcedureFsm` (FSM -- Finite State Machine, англоязычный термин для КА). 

Чтобы не отвлекаться на несущественные детали, вы не будете реализовывать сетевое взаимодействие SMF с другими сервисами, и сфокусируетесь на реализации класса `ReleaseProcedureFsm`. 

Публичные методы этого класса вызываются, когда приходит либо сетевой запрос от другой NF, либо ответ на запрос, сделанный автоматом с помощью интерфейса `IServiceLinks`.

Запросы приходят в автомат только те, которые автомат умеет обрабатывать. Реакция на остальные запросы тривиальная и всегда одинаковая -- запросы отклоняются, и эту логику нет смысла делать частью автомата. 

Полезная нагрузка запросов и ответов на них сделана символичной, нигде даже не передаются идентификаторы сессии, ваш фокус -- логика конечного автомата процедуры, работающей с одной сессией.

В конце работы автомат должен перейти в состояние, в котором его метод `isDone` возвращает истину.

Ваша задача - изучить, как работает очень несовершенная реализация `ReleaseProcedureFsm`, и заменить её на код, обрабатывающий непредусмотренные случаи -- к примеру, ситуацию, когда запрос, который автомат умеет обрабатывать, пришёл не тогда, когда автомат ожидает его появления. 

В качестве примера использования `ReleaseProcedureFsm` в `harness.cpp` дана тривиальная тестовая обвязка. Её доработка не является частью задания, хотя использование юнит-тестов (на основе данной обвязки или любого фреймворка для написания тестов) может помочь вам проверить, корректно ли ваша реализация обрабатывает интересующие вас сценарии.

## Как работает начальная реализация

Начальная реализация полагается на то, что всё идёт по плану - запросы приходят тогда, когда они должны прийти, а на запросы, сделанные автоматом, ответ всегда приходит и он всегда успешный.

В реализации присутствуют следующие шаги:

1. SMF делает запрос к AMF (Namf_Communication_N1N2messageTransfer), чтобы тот передал полезную нагрузку мобильному телефону (N1 - PDU Session Release Command) и базовой станции (N2 - Resource Release Request). 

2. SMF получает ответ N1_N2_TRANSFER_INITIATED на запрос Namf_Communication_N1N2messageTransfer.

3. Базовая станция и телефон обрабатывают NGAP и NAS сообщения и потом посылают свои ответы AMF.

4. AMF присылает в SMF запрос UpdateSmContext с NAS-ответом от телефона, подтверждающим освобождение сессии.

5. AMF присылает в SMF запрос UpdateSmContext с NGAP-ответом от базовой станции, подтверждающим освобождение ресурсов, связанных с сессией.

6. SMF уведомляет AMF, что SmContext (Session Management Context - информация о сессии на стороне SMF) удалён.

7. На этом релиз PDU сессии завершён, автомат закончил работу. 

Обратите внимание, что в коде есть множество ассертов, которые проверяют, что всё идёт благополучно. В вашем решении ассертов быть не должно -- автомат должен корректно обрабатывать все нештатные ситуации. В высоконагруженной системе маловероятные сценарии рано или поздно случаются, и от корректности их обработки зависит стабильность сервиса.

## Нештатные ситуации

Ниже описана часть возможных нештатных ситуаций. 

### В ответ на запрос может прийти ошибка HTTP

В рамках этого практического задания отсылка запросов к другим NF всегда успешна, а отслеживанием сетевого таймаута для получения ответа возложено на внешний код, который вызовет соответствующий метод автомата, передав в качестве ошибки статус 408 Request Timeout. В случае любой ошибки http автомат должен завершить свою работу.

### Другой порядок запросов UpdateSmContext

Два запроса UpdateSmContext (c NAS и с NGAP) могут прийти в SMF в любом порядке и это нормальная ситуация. 

### Неожиданные запросы UpdateSmContext

Никто не гарантирует, что другие компоненты системы ведут так, как разработчик конкретной NF ожидает. Поэтому разработчик не должен полагаться на это и в непонятной ситуации не завершать работу SMF по ассерту, а корректно обрабатывать её.

Чтобы не усложнять автомат, достаточно отклонять UpdateSmContext с причиной UNSPECIFIED_NF_FAILURE во всех ситуациях, когда автомат не ожидает прихода запроса UpdateSmContext.

### Запрос N1N2messageTransfer вернул N1_MSG_NOT_TRANSFERRED или FAILURE_CAUSE_UNSPECIFIED

Эта ситуация обрабатывается путём отсылки на AMF нотификации об удалении SmContext. После этого работа автомата завершается.

### Запрос, ожидаемый автоматом, не пришёл

Если хоть один из двух запросов UpdateSmContext не пришёл на SMF, автомат никогда не перейдёт в состояние `state::done`. В отличие от ожидания ответа на http-запрос, тут внешняя среда не позаботится о контроле таймаута и автомат должен сам завершать свою работу по таймеру. Для этого есть методы `IServiceLinks::StartTimer`, `IServiceLinks::StopTimer` и `ReleaseProcedureFsm::TimerExpired`. При срабатывании таймера автомат должен послать нотификацию AMF об удалении SmContext и завершить работу. 

### Повторная отсылка N1N2messageTransfer

По стандарту в случае отсутствия запроса UpdateSmContext с ответом от телефона (NAS), SMF должен делать повторные попытки отослать PDU Session Release Command с помощью N1N2messageTransfer (NGAP сообщение при этом повторно отсылать не надо), пока не поступит запрос UpdateSmContext или не будет сделано максимально допустимое число попыток. Для реализации этой логики используйте методы `IServiceLinks::StartTimer3592`, `IServiceLinks::StopTimer3592` и `ReleaseProcedureFsm::Timer3592Expired`. `Timer3592Expired` будет вызвана несколько раз, при последнем вызове аргумент `last` будет иметь значение истина. При последнем срабатывании таймера автомат должен отослать нотификацию об удалении SmContext и завершить работу.

## Требования к коду

Не добавляйте в класс автомата дополнительные поля -- добавляйте состояния в `enum state`. 

Постарайтесь писать код так, чтобы логику работы автомата было легко понять. Используйте говорящие названия для состояний автомата и для приватных функций автомата, если они вам понадобятся.

Вы можете использовать сторонние библиотеки для создания конечного автомата путём явного задания таблицы переходов (например, boost::SML), но это вовсе не обязательно.

## Сборка и запуск

Проект собирается с помощью CMake и компилятора с поддержкой стандарта C++23 (ради `std::expected`).

```sh
# из каталога проекта
cmake -S . -B build
cmake --build build
```

После сборки в каталоге `build` появится исполняемый файл `pdu-session-release-fsm`, при запуске которого тестовая обвязка создаст экземпляр `ReleaseProcedureFsm` и выполнит тривиальный тест.
